title: Lifecycle and Notifications
---

Earlier ARM64 physical-device debug candidates passed scoped cold-start navigation, fullscreen return, and configuration ZIP round-trip checks. The current startup/update gates, complete script execution, full gesture matrix, release builds and long-running operation still require separate validation. One device's result does not establish compatibility with every phone. The older emulator failures above remain diagnostic examples, not a claim that all current devices exhibit them.

Python is owned by the dedicated backend service, not the Activity. WebView reloads and Activity recreation reconnect instead of starting another Python owner. System Back dismisses overlays/navigation first, then can background the Activity; it is not the scheduler Stop command.

The foreground service uses a low-priority ongoing notification that opens the app. **This version has no notification Start/Stop task actions.** Its Shizuku setup also attempts to suppress BAAS notifications, so drawer visibility alone is not a reliable health check. Use in-app connection/run state and system logs. Background restrictions can still terminate work; do not treat a successful short test as a long-running reliability guarantee.
