Maintenance tasks can delete friends, transmit logs or modify game resources. They are not harmless simply because they avoid combat. These editors use [automatic persistence](../guide/configuration); saving a setting and executing a task are separate operations.

## Friend Cleanup

<img
  className="baas-screenshot"
  src="/media/desktop/en/config-whitelist.webp"
  alt="Current friend cleanup editor with three filters and a friend-code whitelist"
/>

**Deletion warning:** the audited default backend's `module/friend.py` deletes every friend not in `clear_friend_white_list`. It does **not** read the three newer filter fields below. The same limitation was confirmed in the backend downloaded by the fresh Android installation. Do not rely on the filters to protect friends, and do not run cleanup with an empty whitelist unless that deletion is intentional.

| Visible filter                | Saved field                                  | Client validation     |
| ----------------------------- | -------------------------------------------- | --------------------- |
| Level limit                   | `clear_friend_level_limit`                   | Integer at least `-1` |
| Days since last login         | `clear_friend_last_login_time_days`          | Integer at least `-1` |
| Last Total Assault rank limit | `clear_friend_last_total_assault_rank_limit` | Integer at least `-1` |

The UI represents `-1` as disabling a filter. That is an interface convention, not proof the connected backend implements filtering or a particular AND/OR rule. Blank or fractional thresholds block this section's draft commit, including whitelist changes in that draft.

### Edit the Whitelist

Enter a friend code and choose Add, or press Enter after finishing text composition. Leading/trailing whitespace is removed; duplicates are rejected. Validation follows the profile server, not the UI language:

| Server family          | Accepted by this client                                                        |
| ---------------------- | ------------------------------------------------------------------------------ |
| CN, including Bilibili | Seven lowercase ASCII letters/digits                                           |
| Global                 | Eight uppercase ASCII letters                                                  |
| JP                     | Eight characters; the UI does not impose an additional character-pattern check |

Each accepted code appears as a chip. Its remove icon removes whitelist protection; it does not immediately delete the in-game friend. The next cleanup may delete that friend. The list saves as `clear_friend_white_list`. Confirm codes against the actual account and game before enabling cleanup.

## Push Notifications

<img
  className="baas-screenshot"
  src="/media/desktop/en/config-push.webp"
  alt="Push editor with error and completion switches, JSON endpoint and ServerChan key"
/>

| Control               | Configuration                                                                |
| --------------------- | ---------------------------------------------------------------------------- |
| Push after error      | `push_after_error`: send the error payload when the backend reports an error |
| Push after completion | `push_after_completion`: send when the backend finishes the run              |
| JSON push             | `push_json`: receiving URL, **not** a JSON document                          |
| ServerChan            | `push_serverchan`: SendKey, not the full endpoint URL                        |
| Feishu | `push_feishu`: group-bot Webhook URL |
| WeCom | `push_wecom`: group-bot Webhook URL |
| Telegram Bot Token | `push_telegram_bot_token`: Token issued by BotFather |
| Telegram Chat ID | `push_telegram_chat_id`: destination chat or group ID, including negative group IDs |
| Telegram proxy | `push_telegram_proxy`: optional HTTP/HTTPS proxy used by the backend |
| Telegram API address | `push_telegram_api`: optional API base address; blank uses `https://api.telegram.org` |

Webhook URLs, ServerChan SendKey, Telegram Token and proxy are hidden by default;
the eye control reveals one value locally. Chat ID and API address remain
visible. The frontend does not test network reachability or send a test push.
Keep keys and signed URLs out of screenshots, shared profiles and public logs.
Empty endpoint/key values disable the corresponding destination, while other
configured channels can continue to receive notifications.

Telegram notifications require both Token and Chat ID. Filling only one shows
an incomplete-credentials hint while still saving the current values; clearing
either disables Telegram notifications. This integration sends completion/error
notifications, not interactive bot commands. Send the bot a message first when
using a private chat. Chat IDs remain strings so signed and large IDs retain
their exact value.

The optional proxy runs on the script backend. In Docker, `127.0.0.1` means the
container; on Android it means the phone, rather than the browser's computer.
Newer channel controls are disabled with an update-backend message when their
fields are absent from the connected backend snapshot.

The generic JSON destination receives a POST with `Content-Type: application/json`. Example error payload:

```json
{
  "title": "Baas Error",
  "desp": "error..."
}
```

Successful completion uses title `Baas Completed` and description `all activities finished`. JSON and ServerChan adapters treat HTTP 200 as success; Feishu and WeCom also check their response's success code, while Telegram checks its `ok` result. Request failures appear in backend logs; saving a URL is not a test push. ServerChan uses `https://sctapi.ftqq.com/{SendKey}.send`.

## Uncensoring

<img
  className="baas-screenshot"
  src="/media/desktop/en/config-other.webp"
  alt="Other editor with the one-shot uncensor execution command"
/>

The Other category contains an **Execute** command for uncensoring, not a persistent enable switch. It submits `start_fhx` immediately and returns to Home. Do not click it to test whether settings save.

This is a CN-specific game-resource operation. Stop scheduling, check the profile's real package/server, preserve needed game data and confirm backend support before execution. It is not required for ordinary automation and is not a universal repair for recognition failures. Re-enter the game afterward to verify its resource state; future game updates can change that state.

## Other Maintenance Tasks

Mail, daily rewards, club AP, pass rewards and MomoTalk are selected in the task list rather than through additional controls in these three categories. Review task timing and dependencies in [Scheduler](../guide/scheduler). Even reward collection changes account state, while MomoTalk may advance conversations. Supervise the first run and inspect logs instead of assuming every maintenance task is safe unattended.
