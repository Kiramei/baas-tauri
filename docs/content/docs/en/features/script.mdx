## Startup and Completion

| Control           | Saved field | Meaning / limitation                                                                                |
| ----------------- | ----------- | --------------------------------------------------------------------------------------------------- |
| Autostart         | `autostart` | Stores the legacy backend/launcher startup flag; it is not an operating-system startup registration |
| Completion action | `then`      | Do nothing, exit BAAS, exit emulator, exit both, or shut down the host                              |

In the audited Tauri client, no startup consumer of `autostart` was found outside the configuration editor. Do not rely on this switch alone for unattended app-launch scheduling; verify the actual backend/launcher behavior.

Completion values retain the backend strings `无动作`, `退出 Baas`, `退出 模拟器`, `退出 Baas 和 模拟器` and `关机`, even in an English UI. The audited backend applies `then` when its scheduler considers the next wait long enough, not after each individual task.

**Shutdown and exit commands affect the real environment.** Keep Do nothing while testing. A saved completion action is not a confirmation preview, and Android must not be assumed to implement desktop emulator/host shutdown identically.

## Screenshot Interval

`screenshot_interval` is the backend recognition capture interval, in seconds. It must be finite and at least `0.1`; blank, nonnumeric or smaller values block the section's draft commit. The input uses a 0.1 step.

It is not the game FPS, the display preview FPS, a video bitrate or an end-to-end reaction-time guarantee. Reducing it increases requested capture frequency, but processing, transport and game transitions still determine actual behavior. See [Performance](../reference/performance) for bounded measurements rather than assuming a fixed speedup.

## Screenshot and Control Methods

The two dropdowns use the connected backend's supported lists. A saved unknown method is preserved as a visible choice; its presence does not prove availability.

| Method       | Capture / control context                                                       |
| ------------ | ------------------------------------------------------------------------------- |
| ADB          | Device capture and input over ADB                                               |
| Nemu         | MuMu-specific capture/control integration; requires a matching environment      |
| uiautomator2 | Device automation connection; backend and device setup must agree               |
| scrcpy       | Device video/control integration; video decoding can affect recognition quality |
| MSS          | Desktop screen capture; not a device input method                               |
| PyAutoGUI    | Desktop screen capture/mouse input; window placement and focus matter           |

Saved fields are `screenshot_method` and `control_method`. The help below each selector changes with the selected method. Not every method appears in both lists or on every backend/platform. Set a compatible pair, then verify actual screenshots and clicks; changing only the dropdown is not a driver installation.

If logs repeat `tentative click` without progress, inspect the actual game image, active window/device, control method and overlays. Do not keep increasing click frequency when the coordinates or recognition image are wrong.

## Recognition Baseline

The historical backend guide uses a stable 16:9 image, commonly `1280×720`, 60 FPS, compatible rendering, post-processing/anti-aliasing enabled and combat letterboxing disabled. These are recognition setup references, **not this documentation's performance benchmark**. Verify the current game's available settings rather than assuming the labels are universal.

Dynamic memorial lobbies, HDR/color transforms, overlays and translation patches that alter buttons/text can make screenshots differ from recognition templates. Restore an unmodified, clearly visible game UI before diagnosing task logic.

## Android

Android hides the screenshot/control dropdowns and uses `android_local` internally. Its editor saves common fields without overwriting the desktop method fields. Local capture/input requires the running, authorized Shizuku service and the correct profile/game display; it is not desktop ADB selection. See [Android Client](../guide/android).
