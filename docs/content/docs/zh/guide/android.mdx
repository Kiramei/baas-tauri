APK 内含 Python 运行时，首次启动还需下载后端。自动化控制依赖单独安装、启动并授权的 Shizuku。

## 安装与准备

从项目 [Releases](https://github.com/Kiramei/baas-tauri/releases) 获取可信 Android 构建，按设备真实架构选择，而非只看游戏架构。Android 提示时，为所用浏览器/文件管理器允许安装。APK 声明的最低版本为 Android 7.0/API 24；原生游戏采集需要 Android 8.0/API 26 及以上。满足版本要求后，仍需检查设备是否支持特权显示。

首次启动保持网络可用。准备页分五个阶段：

| 阶段         | 实际工作                                          |
| ------------ | ------------------------------------------------- |
| 应用数据     | 准备私有目录，处理受支持的旧数据迁移与备份        |
| 安装运行环境 | 检查内嵌 Python，下载/安装后端并应用 Android 适配 |
| 启动本地服务 | 在独立后端服务进程中启动 Python                   |
| 验证连接     | 建立经过身份验证的加密客户端/后端会话             |
| 同步配置     | 加载配置档与任务，OCR 可继续在后台初始化          |

展开阶段可查看 stdout/stderr 终端。显示“准备中”不代表安装完成；重试前保留完整错误输出，下载、解压或更新时不要强行关闭。

正常运行时和配置保存在应用私有目录，广泛共享存储权限不是启动失败的通用修复。卸载或清除数据可能移除运行时和配置档，操作前先导出需要的配置。

## Shizuku 授权

从 [Shizuku 官方下载页](https://shizuku.rikka.app/download/)单独安装，根据设备情况启动其服务后返回 BAAS。[官方设置指南](https://shizuku.rikka.app/guide/setup/)说明 root、无线调试及电脑辅助启动方式。

| BAAS 检测状态    | 需要进行的操作                                      |
| ---------------- | --------------------------------------------------- |
| 未安装           | 单独安装 Shizuku，没有可从 BAAS 解出的内置安装器    |
| 已安装但未运行   | 打开 Shizuku 并启动服务                             |
| 正在运行但未授权 | 在 BAAS 点击允许访问，再确认真正的 Shizuku 权限弹窗 |
| 已就绪           | 关闭提示，再明确重试原来的启动动作                  |
| 状态检查失败     | 查看错误并重试检查，不要凭旧 Live 标志认定授权有效  |

启动调度和启动后台游戏都会检查当前权限。授权后不会暗中续执行之前被阻止的命令；停止调度是独立操作，权限失效时仍应能够停止。

**使用当前安装的 Shizuku 界面提供的启动指令。** 旧说明使用外部 `start.sh`，[v13.6.0](https://github.com/RikkaApps/Shizuku/releases/tag/v13.6.0) 已改用安装目录内的原生可执行文件。不要复制另一设备的安装路径。

## 后台游戏与预览

授权后选中匹配配置档，点击首页游戏区域的播放图标。BAAS 创建本机后台显示并启动对应包；该显示是共享资源，另一配置档正在运行时会阻止冲突启动。恢复出来的旧显示也不能自动视为属于当前配置档。

<AndroidGameDemo locale="zh" />

原生预览是**只读的**。点击画面会打开三个原生图标：

| 图标动作 | 行为                                                 |
| -------- | ---------------------------------------------------- |
| 关闭     | 请求停止当前调度，释放后台显示并结束其游戏进程         |
| 接管     | 把已有游戏任务移到主显示供手动操作，随后释放嵌入会话 |
| 重启     | 关闭当前会话，再创建显示并启动所选游戏；不会重新启动调度 |

<img
  className="baas-screenshot baas-mobile-screenshot"
  src="/media/android/zh/game-controls.webp"
  alt="原生预览顶部从左到右为关闭、接管和重启按钮"
/>

点击预览里的游戏按钮不会直接发送游戏输入；需要手动操作时使用接管。菜单和弹窗出现时会隐藏原生预览，避免覆盖界面控件；回到可见首页后恢复预览归属。切到其他页面隐藏的是视图，不一定停止后台游戏或 Python 服务。

关闭路径会发送停止请求，但不会等待后端确认。接管、重启或关闭前，先用底部停止按钮停止调度，核对运行状态和日志，再操作游戏会话。底部停止本身不会关闭游戏显示。接管保留已有游戏进程，便于继续手动操作。

### 预览状态

状态标签在[虚拟屏修复构建](https://github.com/Kiramei/baas-tauri/commit/e3ed51d7339ea33dc5b6a397e1368b0dfee48e19)中加入。包含[消费端进度检查](https://github.com/Kiramei/baas-tauri/commit/532f785b)和[唯一缓冲帧计数](https://github.com/Kiramei/baas-tauri/commit/128983b8)的 APK 按以下规则判断；早期构建的 Live 标志可能高估画面更新。

| 状态 | 含义与检查 |
| ---- | ---------- |
| 等待画面 | 采集、GPU 提交、屏幕消费三个阶段中，至少一个尚未收到帧；冷启动先等加载，再检查 Shizuku 和游戏进程 |
| 黑屏 | 已有帧，但内容仍黑；确认游戏位于目标显示，查看采集错误 |
| 画面未更新 | 尚未观察到三个阶段各自的计数增长，或其中任一阶段连续约两秒未增长；切回首页并关闭遮挡预览的菜单后再检查 |
| 实时 | 三个阶段最近约两秒内各有进度，且采集内容有非黑像素 |
| 连接异常 | 原生连接或预览调用报错；重新核对授权、服务状态和错误日志 |

实时只反映画面通路，不能证明账号已登录、点击有效或任务成功。任务验收还要核对日志中的任务结果和实际游戏状态。屏幕消费计数只记录不同的正 `SurfaceTexture.timestamp`，重复重绘同一缓冲区不计数；不同缓冲区也可能包含相同像素。反复读取同一张缓存 PNG，同样不能算作新的游戏帧。

[本机性能实测](../reference/performance#android-本机截图)单独测量截图调用和输入确认。截图耗时较低并不保证预览流畅；排查停帧时，对照[原生预览链路](../reference/client-architecture#android-原生预览与截图)定位卡住的阶段。

### 游戏跳回主屏或预览停在启动图

旧构建在 MuMu Android 15、x86_64、Shizuku ADB 模式与 B 服游戏 3.0.2 的组合中，曾出现后台显示创建成功，游戏的 Unity Activity 却被系统拒绝放入该显示、转到主屏，随后预览变黑的情况。修复构建增加了显示任务恢复、焦点恢复和帧状态检查；同一模拟器的短测曾通过持续预览，以及原生截图、识别和点击参与的启动导航。后续冷启动复测仍出现停在开场图的情况，因此预览稳定性尚未确认修复。此前的帧计数和短测结果不能证明实际游戏画面始终流畅，也没有覆盖全部业务任务、其他手机或长期后台运行。

若游戏退出时日志出现 `DeadSystemException`，同时系统日志记录 `system_server` 崩溃，先检查 Android 系统进程和 Shizuku 的连接状态。该组合已在上述模拟器复现；崩溃发生在系统窗口任务可见性处理期间，具体触发原因仍在排查。系统自行恢复后，Shizuku 可能需要重新以 ADB 模式启动，旧游戏会话不能继续使用。

遇到相同现象，先停止调度并关闭后台显示，检查系统日志中是否出现 `Not allow to launch ... on display`。确认 APK 是否含上述修复，更新后重新创建游戏会话。提高码率、缩短截图间隔或重新安装游戏都不能解决显示放置权限的问题。Shizuku ADB 模式已在该模拟器通过这些验证，Root 不是本机控制的统一前提。

冷启动后画面横倒、只有半屏内容或带大块黑边时，还需检查虚拟屏方向配置。[后续方向修复](https://github.com/Kiramei/baas-tauri/commit/8e38508f160a29d784125970c2dad00d3c9e347d)等待系统登记显示后再锁定方向，并阻止启动页给横屏显示应用竖屏旋转变换。更新到包含此修复的 APK 后，关闭旧会话再重新启动游戏；无需修改手机主屏的旋转设置。

开发者可对照 `adb shell dumpsys activity activities` 和 `adb shell dumpsys display`，确认实际游戏 Activity 所在显示，以及虚拟屏是否带 `FLAG_TRUSTED`。[Android 15 的显示放置检查](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/services/core/java/com/android/server/wm/ActivityTaskSupervisor.java)会限制普通应用在非可信显示上启动 Activity；BAAS 通过特权服务启动第一个页面成功，也不足以保证游戏后续页面能留在同一显示。该检查是排查线索，不能据此认定所有 Android 设备都有相同问题。

## 生命周期与通知

Python 由独立后端服务持有，不由 Activity 持有；WebView 重载或 Activity 重建应重新连接，而不是再启动一个 Python 所有者。系统返回键先处理弹窗和页面导航，再可能将 Activity 放到后台，不是调度停止按钮。

前台服务使用低优先级常驻通知，点击可打开应用；**没有通知栏启动/停止任务动作**。其 Shizuku 初始化还会尝试抑制 BAAS 通知，因此是否出现在通知抽屉不能单独作为健康指标。使用应用内连接/运行状态和系统日志判断；系统后台限制仍可能终止工作，短时测试成功不代表长期运行可靠。

## 更新与排查

后端更新使用应用配置的来源，并显示进度和输出；失败时保留启动、系统及更新日志。下载请求失败、身份验证失败、游戏识别失败属于不同层，调截图间隔不能修复下载。

Android 手动后端更新入口不会等待所有任务停止。更新前先核对各配置档的运行状态并停止任务。当前更新命令会延后服务重启；磁盘同步成功、WebView 重载和新 Python 代码生效需要分别确认。同步成功后，如需重新启动后端进程，先停止全部任务、关闭后台游戏显示，再到 Android 系统设置的应用信息中**强行停止 BAAS**，重新打开并核对后端版本、日志及有监督的运行结果。返回键或划掉界面可能保留服务进程。部分服务文件仍由 APK 匹配覆盖层提供，仅更新后端仓库不会替换这些文件。[更新器内部机制](../reference/updater-internals)说明具体流程和限制。

| 现象               | 核对项目                                               |
| ------------------ | ------------------------------------------------------ |
| APK 无法安装       | 真实 CPU ABI、Android 版本、可信安装权限、已有包和签名 |
| 准备失败           | 对应阶段终端、网络/来源、应用私有存储                  |
| 游戏未安装提示     | 当前配置档精确对应的地区包名                           |
| Shizuku 不可用     | 安装、运行、授权三个独立状态                           |
| 黑屏、画面未更新或旧版 Live 停在启动图 | 实际游戏任务与显示归属、修复构建、原生采集错误和 ABI 兼容 |
| OCR 初始化失败 | 看具体动态库/模型错误；界面已经连接不代表 OCR 就绪 |
| 后端断连           | 服务/进程日志及后台限制，不仅看通知是否显示            |

### 与电脑端 uiautomator2 共用设备

Android BAAS 的本机设备桥接监听**设备自身**的 `127.0.0.1:7912`，`/version` 返回 `baas-shizuku-display-1`。它供内嵌运行时使用，受私有令牌保护，接口也与标准 atx-agent 不同。电脑端普通 uiautomator2 经 ADB 转发访问同一端口时，可能收到 HTTP 403，继而报 `PIL.Image.open` 无法识别图片。

这类错误先检查端口对应的服务。不要关闭桥接认证或把应用私有令牌填入普通 atx-agent 客户端。需要切换到电脑端 uiautomator2 时，先停止任务，再通过系统应用信息停止 Android BAAS 的进程，确认原监听释放后准备标准 atx-agent；仅把界面切到后台不会停止其服务。反向切回 Android BAAS 前，同样处理另一服务的端口占用。停止进程会中断该客户端当前的后台任务。

## 模拟器 ABI 兼容

部分 x86_64 模拟器可安装 ARM64 应用，但 Shizuku 用户服务仍运行于 x86_64 进程。加载 ARM64 采集库时会出现 `EM_AARCH64` 与 `EM_X86_64` 不匹配错误，需要使用与该进程架构匹配的构建。游戏停在启动图时，还应检查游戏 Activity 的显示归属与原生采集日志。

模拟器的 `uname -m` 也可能报告 ARM，而 APK 内的 Python 实际加载 x86_64 库。OCR 此时误选 ARM64 库会在 `dlopen` 阶段失败。修复构建按内嵌解释器库的 ELF 架构选择 OCR；排查时保留错误中的目标库和期望架构，不要只用系统报告的架构决定安装哪个 OCR 包。任务启动仍会检查 OCR 是否完成初始化。

更多排查见[故障排除](../reference/troubleshooting#android-客户端异常)。
