授权后选中匹配配置档，点击首页游戏区域的播放图标。BAAS 创建本机后台显示并启动对应包；该显示是共享资源，另一配置档正在运行时会阻止冲突启动。恢复出来的旧显示也不能自动视为属于当前配置档。

上面的演示与下图记录旧版内嵌预览；当前版本新增原生全屏手动控制。内嵌预览仍为**只读**，点击画面打开原生控件：

| 图标动作 | 行为                                                 |
| -------- | ---------------------------------------------------- |
| 关闭     | 请求停止当前调度，释放后台显示并结束其游戏进程         |
| 全屏 / 接管 | 在原生全屏中操作同一后台显示和游戏进程，保留嵌入会话 |
| 重启     | 关闭当前会话，再创建显示并启动所选游戏；不会重新启动调度 |

内嵌预览不发送游戏点击；需要手动操作时进入全屏。全屏浮动菜单可拖动，提供**返回内嵌画面**和**关闭游戏**；返回内嵌画面保留同一游戏会话。菜单和弹窗出现时会隐藏内嵌预览，避免覆盖界面控件；回到可见首页后恢复。切到其他页面不会自动停止后台游戏或 Python 服务。

关闭路径会发送停止请求，但不会等待后端确认。底部停止本身不会关闭游戏显示。进入全屏也不会自动停止调度；自动化输入优先，并会取消或阻止冲突的手动手势。手动操作仍会改变游戏状态，建议先停止调度并核对日志，避免相互干扰。重启会结束当前会话并重新创建显示，不会重新启动调度。

预览黑屏、停帧或游戏退出时，先停止调度并关闭后台会话，检查预览状态、启动与系统日志后再新建会话。右上角预览状态保留，单独的设备启动按钮已隐藏。

## 预览状态

状态标签在[虚拟屏修复构建](https://github.com/Kiramei/baas-tauri/commit/e3ed51d7339ea33dc5b6a397e1368b0dfee48e19)中加入。包含[消费端进度检查](https://github.com/Kiramei/baas-tauri/commit/532f785b)和[唯一缓冲帧计数](https://github.com/Kiramei/baas-tauri/commit/128983b8)的 APK 按以下规则判断；早期构建的 Live 标志可能高估画面更新。

| 状态 | 含义与检查 |
| ---- | ---------- |
| 等待画面 | 采集、GPU 提交、屏幕消费三个阶段中，至少一个尚未收到帧；冷启动先等加载，再检查 Shizuku 和游戏进程 |
| 黑屏 | 已有帧，但内容仍黑；确认游戏位于目标显示，查看采集错误 |
| 画面未更新 | 尚未观察到三个阶段各自的计数增长，或其中任一阶段连续约两秒未增长；切回首页并关闭遮挡预览的菜单后再检查 |
| 实时 | 三个阶段最近约两秒内各有进度，且采集内容有非黑像素 |
| 连接异常 | 原生连接或预览调用报错；重新核对授权、服务状态和错误日志 |

实时只反映画面通路，不能证明账号已登录、点击有效或任务成功。任务验收还要核对日志中的任务结果和实际游戏状态。屏幕消费计数只记录不同的正 `SurfaceTexture.timestamp`，重复重绘同一缓冲区不计数；不同缓冲区也可能包含相同像素。反复读取同一张缓存 PNG，同样不能算作新的游戏帧。

[本机性能实测](../reference/performance#android-本机截图)单独测量截图调用和输入确认。截图耗时较低并不保证预览流畅；排查停帧时，对照[原生预览链路](../reference/client-architecture#android-原生预览与截图)定位卡住的阶段。

## 游戏跳回主屏或预览停在启动图

旧构建在 MuMu Android 15、x86_64、Shizuku ADB 模式与 B 服游戏 3.0.2 的组合中，曾出现后台显示创建成功，游戏的 Unity Activity 却被系统拒绝放入该显示、转到主屏，随后预览变黑的情况。修复构建增加了显示任务恢复、焦点恢复和帧状态检查；同一模拟器的短测曾通过持续预览，以及原生截图、识别和点击参与的启动导航。后续冷启动复测仍出现停在开场图的情况，因此预览稳定性尚未确认修复。此前的帧计数和短测结果不能证明实际游戏画面始终流畅，也没有覆盖全部业务任务、其他手机或长期后台运行。

若游戏退出时日志出现 `DeadSystemException`，同时系统日志记录 `system_server` 崩溃，先检查 Android 系统进程和 Shizuku 的连接状态。该组合已在上述模拟器复现；崩溃发生在系统窗口任务可见性处理期间，具体触发原因仍在排查。系统自行恢复后，Shizuku 可能需要重新以 ADB 模式启动，旧游戏会话不能继续使用。

遇到相同现象，先停止调度并关闭后台显示，检查系统日志中是否出现 `Not allow to launch ... on display`。确认 APK 是否含上述修复，更新后重新创建游戏会话。提高码率、缩短截图间隔或重新安装游戏都不能解决显示放置权限的问题。Shizuku ADB 模式已在该模拟器通过这些验证，Root 不是本机控制的统一前提。

冷启动后画面横倒、只有半屏内容或带大块黑边时，还需检查虚拟屏方向配置。[后续方向修复](https://github.com/Kiramei/baas-tauri/commit/8e38508f160a29d784125970c2dad00d3c9e347d)等待系统登记显示后再锁定方向，并阻止启动页给横屏显示应用竖屏旋转变换。更新到包含此修复的 APK 后，关闭旧会话再重新启动游戏；无需修改手机主屏的旋转设置。

开发者可对照 `adb shell dumpsys activity activities` 和 `adb shell dumpsys display`，确认实际游戏 Activity 所在显示，以及虚拟屏是否带 `FLAG_TRUSTED`。[Android 15 的显示放置检查](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/services/core/java/com/android/server/wm/ActivityTaskSupervisor.java)会限制普通应用在非可信显示上启动 Activity；BAAS 通过特权服务启动第一个页面成功，也不足以保证游戏后续页面能留在同一显示。该检查是排查线索，不能据此认定所有 Android 设备都有相同问题。
