Tauri 安装器会管理后端。手动启动适用于源码开发、隔离测试和部署独立服务；不要同时启动第二个进程占用当前客户端的端口、配置目录或设备。

## 选择入口

| 入口 | 行为 |
| ---- | ---- |
| `main.service.py` | 启动 HTTP/WebSocket 服务，按配置接入本机 Pipe 或共享内存，调度由服务命令控制 |
| `cli.example.py` | 初始化旧版 `Main` 与设备线程，直接运行脚本内列出的任务 |
| `main.py` | 旧版主程序入口，不是只读服务诊断命令 |

`cli.example.py` 与 `main.py` 都可能操作游戏。验证网络或认证时使用 Service，先关闭自动启动和任务开关，不要执行 CLI 示例来测试依赖是否安装完整。

## 环境准备

在独立后端检出目录创建虚拟环境，按项目的 Service 依赖安装：

```bash
python -m venv .venv
python -m pip install -e ".[service]"
```

第二条需使用已激活虚拟环境的 Python，或改成该环境解释器的完整路径。项目元数据声明 Python `>=3.9`，依赖版本和平台仍会限制可安装组合；这不是所有更高 Python 版本均经过验证的承诺。安装器使用的平台依赖列表及 OCR 要求见[后端开发](./backend-development)。旧文档固定 Python 3.9.21、安装通用 `requirements.txt` 的命令不适用于当前 Service 依赖划分。

## 启动 Service

```bash
python main.service.py --host 127.0.0.1 --port 8190 --log-level info
```

| 参数 | 默认与作用 |
| ---- | ---------- |
| `--host` | `BAAS_SERVICE_HOST`，未设置为 `0.0.0.0`；本机开发显式指定 `127.0.0.1` |
| `--port` | `BAAS_SERVICE_PORT`，未设置为 `8190` |
| `--log-level` | 默认 `info`，控制 Uvicorn 日志等级 |
| `--reload` | 开发重载；运行真实任务或共享目录时避免使用 |
| `--pipe-name` | 启用指定本机 Pipe，互斥于 `--shm-name` |
| `--shm-name` | 打开受管理共享内存会话，互斥于 `--pipe-name` |
| `--ocr-update-check` | 显式启用启动时 OCR 更新检查 |
| `--no-ocr-update-check` | 跳过更新检查；不等于禁用 OCR 或忽略缺失模型 |

`BAAS_SERVICE_OCR_UPDATE_CHECK` 默认启用；值为 `0`、`false`、`no`、`off` 时关闭，命令行标志覆盖环境默认。传入 Pipe/共享内存参数时会清除另一种本机传输的环境变量；如果只通过环境同时启用两者，服务生命周期会拒绝启动。

本机 IPC 参数由客户端创建和管理，随意填写名字不会创建可用的对端会话。WebUI 仍使用已认证 WebSocket。参数/环境与安全边界见[服务接口](./backend-service#本机-pipe-与共享内存)。

脚本在当前工作目录写 `.pid`，退出时尝试删除。不要让多个进程共用同一个工作目录的 `.pid`。Ctrl+C 请求服务关闭，资源释放和任务协作停止需要时间；不要把 PID 文件消失当成任务已经成功。

### 只检查入口

```bash
python main.service.py --help
```

帮助命令可查看实际构建支持的参数，不会启动 Service 或运行游戏任务。该脚本仍会初始化诊断日志并执行退出清理，因此也应在隔离目录运行，避免触及另一个进程的 `.pid` 文件。`GET /health` 可检查监听中的服务，但不能证明认证、配置、OCR 与设备全部就绪。

`--host 0.0.0.0` 会监听所有网卡。独立远程部署前完成密码初始化，使用匹配的私有签名密钥与前端公钥、HTTPS/WSS、网络访问限制和适当代理路由；详见[控制认证](./backend-service#控制认证)。

## 旧 CLI 示例

先阅读 `cli.example.py`，再在自己的隔离副本中修改配置目录和任务列表。需要执行时，使用解释器运行脚本，例如 `python cli.local.py`；使用 PDM 时为 `pdm run python cli.local.py`。

当前示例创建 `Main(ocr_needed=["en-us", "zh-cn"])`、`ConfigSet(config_dir="default_config")` 和 `Baas_thread`，设置 OCR 并初始化数据，然后用 `asyncio.gather()` 并发安排两组协程：

| 组 | 执行内容 |
| -- | -------- |
| 常规任务 | 重启、咖啡厅、课程、领奖、社团、邮件、两类商店、制造、悬赏等脚本内任务 |
| 竞技场 | 五次竞技场任务，前四次之间各等待 60 秒 |

设备任务通过 `asyncio.to_thread()` 执行，示例的共享 `threading.Lock` 串行化 `baas.solve()`；协程并发不等于同时向设备输入。这里的顺序、等待与 Service 调度器的时间/前后置依赖无关。

该文件在顶层调用 `asyncio.run(main())`，**导入它也会执行任务**。它包含商店等资源消费操作，不能当成无副作用的库或健康检查。示例没有展示完整的异常恢复与设备资源关闭协议；用于系统计划任务前，还需处理重入、退出码、超时、凭据和日志隐私。

## 验证与排查

在隔离检出中运行：

```bash
python -m compileall -q service
python -m pytest tests/service
```

测试会创建临时配置和认证数据，不能在正在服务真实客户端的目录中直接运行。命令返回成功只证明对应检查通过；网络部署、打包平台、OCR 模型和真实游戏任务仍需分别验证。

服务已连接却没有任务时，先看认证与初始化门、配置档任务开关、调度状态和日志。调度已停止但进程还在时，检查服务本身是否仍应常驻；调度器停止不是关闭整个 Service。更多执行边界见[后端开发](./backend-development)。
