---
title: 后端与 OCR 准备
---

首次安装默认克隆稳定版后端 `pur1fying/blue_archive_auto_script` 的 `master` 分支。需要开发版时，将容器的 `command` 设为 `https://github.com/Kiramei/baas-dev.git`。已有数据卷沿用其 Git 来源，分支由 `BRANCH` 指定。已有 Git 工作区只进行快进更新，不自动丢弃或暂存本地修改。完整 OCR 安装会保留；缺少文件时按启动配置尝试修复，已有配置和输出保留。

在 **设置 → 更新** 点击 **检查更新**。发现新版本后，点击 **更新 BAAS**。侧栏也提供同一操作。容器会停止任务、将已安装的分支快进到新提交，并重启 Python 服务。页面确认新进程的提交后重新加载。配置档和登录数据保存在原来的 `/app` 卷中。启用 `no_update` 会同时关闭页面更新。

点击 **测试所有方法**，可以查看容器从所选渠道的每个源读取最新提交号所用的时间。成功时显示提交号，失败时显示该源的错误原因。

ARM64 镜像内置由 [BAAS_Cpp](https://github.com/pur1fying/BAAS_Cpp/tree/753901eb4678693992ef33e58abaa4d854bbdb63) 源码构建的 Linux OCR，首次启动时会安装内置包。开启启动更新时，从 AMD64 迁移的数据卷中的 OCR 二进制会按架构替换，OCR 配置和输出会保留。AMD64 镜像从 [BAAS_Cpp_prebuild](https://github.com/pur1fying/BAAS_Cpp_prebuild/tree/linux-x64) 下载默认 OCR 包。

完全离线部署可在 `/app/setup.toml` 中使用：

```toml
[general]
no_update = true
```

这会禁止启动阶段 Git 更新及 OCR 下载，空目录无法靠它完成安装。需要先准备有效后端 `main.service.py`、Python 依赖及匹配架构的 OCR。`BAAS_SERVICE_OCR_UPDATE_CHECK=0` 只跳过后端 OCR 更新检查，不能代替完整的离线文件准备。
