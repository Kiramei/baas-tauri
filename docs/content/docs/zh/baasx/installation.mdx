## 选择安装方式

| 方式                  | 电脑需要什么                             | 适合谁                     |
| --------------------- | ---------------------------------------- | -------------------------- |
| npm 注册表包          | Node.js 20.3+ 或 Deno                    | 全局安装 `baasx` 命令      |
| 原生发行包 `.tar.gz`  | 对应操作系统和架构，无需 Bun / Rust      | 希望解压即用               |
| Bun 发行包 `-bun.tgz` | Bun 1.4.4+，无需 Rust                    | 已经使用 Bun               |
| 从源码启动或构建      | Bun 1.4.4+、Rust 1.95+ 和 C/C++ 编译工具 | 尚无发行包，或需要开发版本 |

## npm 注册表安装

使用 npm、Bun、pnpm、Yarn 或 cnpm 安装时，需先安装 Node.js 20.3 或更新版本。Deno 可直接运行。选择一种已安装的工具：

<PackageManagerInstall locale="zh" />

全局安装完成后运行 `baasx --help` 或 `baasx --demo --lang zh`。请确保所用包管理器的全局可执行文件目录已加入 PATH。pnpm 提示找不到全局目录时可运行 `pnpm setup` 并重新打开终端。Yarn 1 可用 `yarn global bin` 查看目录。Bun 默认使用 `~/.bun/bin`，也可能由配置指定其他目录。

选项卡中的 Yarn 全局安装命令适用于 Yarn 1。Yarn 2 及更新版本可使用 `yarn dlx --package @kiramei/baasx baasx --help` 临时运行 BAASX。

cnpm 默认使用 npm 镜像，新版本可能需要等待镜像同步。若暂时找不到包，可直接使用上面的 npm 命令。

Deno 的 `-A` 为启动器授予全部权限。安装后需将 Deno 和其全局可执行目录（默认 `~/.deno/bin`）加入 PATH。Deno 2.9 起默认等待版本发布满 24 小时；如需立即安装，可在 Deno 2.9 或更新版本的命令中加入 `--min-dep-age=0`。

两个入口安装同一款 JavaScript CLI。包管理器根据系统和 CPU 自动选择同版本的运行时。Linux、macOS 和 Windows 各提供 x64、ARM64 CLI。本地 OCR 当前支持 Linux x64、macOS ARM64 和 Windows x64，其他平台可连接远程服务或使用演示模式。GitHub Packages 发布带作用域的包。

独立版本发布后，可从 [GitHub Releases](https://github.com/Kiramei/baas-tauri/releases?q=baasx-v) 的 `baasx-v<版本>` 下载归档。桌面客户端的 Latest 安装包为另一发行物。

## 原生发行包

发布后，按下表选择资产，`<版本>` 替换为实际 Release 版本：

| 电脑              | 原生归档                          |
| ----------------- | --------------------------------- |
| Windows x64       | `baasx-<版本>-Windows-X64.tar.gz` |
| Linux x64         | `baasx-<版本>-Linux-X64.tar.gz`   |
| Apple Silicon Mac | `baasx-<版本>-macOS-ARM64.tar.gz` |
| Windows ARM64 | `baasx-<版本>-Windows-ARM64.tar.gz` |
| Linux ARM64 | `baasx-<版本>-Linux-ARM64.tar.gz` |
| Intel Mac | `baasx-<版本>-macOS-X64.tar.gz` |

### Windows PowerShell

在下载目录打开 PowerShell，替换文件名中的版本：

```powershell
New-Item -ItemType Directory -Force baasx
tar -xzf .\baasx-<版本>-Windows-X64.tar.gz -C .\baasx
Set-Location .\baasx
.\baasx.exe --demo --lang zh
```

体验后退出，用 `.\baasx.exe --lang zh` 连接真实服务。建议在支持 Unicode、颜色和鼠标的现代终端中使用。

### Linux / macOS

以 Linux x64 为例，Mac 替换为自己的资产名：

```sh
mkdir -p baasx
tar -xzf baasx-<版本>-Linux-X64.tar.gz -C baasx
cd baasx
chmod +x baasx runtime/baas-cli-runtime
./baasx --demo --lang zh
```

解压后保留以下相对目录：

```text
baasx/                   # 解压目录，可自行改名
├── baasx                # Windows 为 baasx.exe
├── runtime/
│   └── baas-cli-runtime # Windows 带 .exe
├── README.md
├── README_zh.md
└── LICENSE
```

**不要只复制主程序而丢弃 `runtime/`。** 加入 PATH 时指向整个解压目录，或创建指向原程序的启动方式。Release 中的 `SHA256SUMS` 用于与下载归档的 SHA-256 对照；Linux 可在归档目录运行 `sha256sum --check --ignore-missing SHA256SUMS`，PowerShell 用 `Get-FileHash -Algorithm SHA256 <文件名>` 与清单比对。

## Bun 发行包

先确认 `bun --version` 满足 1.4.4+，再安装与系统和架构对应的本地附件：

```sh
bun add -g ./baasx-<版本>-Linux-X64-bun.tgz
baasx --help
baasx --demo
```

Windows 和 macOS 使用各自的包名。全局安装后若找不到命令，检查 Bun 的全局 bin 目录是否在 PATH 中。发布包已带 JS 和安装组件，不应临时调用 Cargo。

## 从源码启动

源码开发分支为 `baasx-dev`。以下固定版本示例需要 Node.js（含 npm）、Git、Rust 工具链和本机 C/C++ 构建工具，再执行：

```sh
git clone --branch baasx-dev https://github.com/Kiramei/baas-tauri.git
cd baas-tauri
npm exec --yes --package=bun@1.4.4-canary.20261105.1 -- bun install --frozen-lockfile
npm exec --yes --package=bun@1.4.4-canary.20261105.1 -- bun run baasx --demo --lang zh
```

上例通过 npm 临时使用项目固定的 Bun，不替换系统 Bun。已安装满足要求的 Bun 时可用 `bun install --frozen-lockfile` 和 `bun run baasx --demo`。首次启动会构建无界面 Rust 安装组件，之后增量复用。

构建可直接运行的本机包：

```sh
npm exec --yes --package=bun@1.4.4-canary.20261105.1 -- bun run baasx:binary
./baasx/dist/baasx --demo
```

Windows 使用 `.\baasx\dist\baasx.exe`。构建按当前系统和架构进行。二进制瘦身要求 `baasx/package.json` 固定的编译器和完整 revision；不是任意新版 Bun 都支持同样的裁剪。`--no-trim` 可构建完整运行时版本，代价是体积增大：

```sh
npm exec --yes --package=bun@1.4.4-canary.20261105.1 -- bun run baasx:binary --no-trim
```

## 首次安装本地环境

1. 去掉 `--demo` 启动，选择语言。
2. 选择本地安装，检查安装位置并明确确认。
3. 等待私有 Python、后端、OCR 和依赖安装完成。每个步骤可展开查看日志，滚轮或 PageUp / PageDown 查看进度。
4. 连接建立后进入总览，使用 `/profiles` 或 `/new-profile` 准备配置档。
5. 用 `/devices` 检查设备，再按[入门流程](./index#十分钟完成第一次运行)配置并试跑。

已有工作台里可用 `/install` 打开安装入口、`/local` 连接本地环境。运行中 Esc 取消安装或更新；下载失败时先展开失败步骤，依据错误修复网络或依赖再重试。

使用 `/uninstall` 卸载本地后端程序，确认时会显示目录；配置和用户数据会保留。命令行也可使用 `baasx uninstall`，非交互执行需加 `--yes`。

本地环境默认在 `<CLI配置目录>/runtime`，使用支持 `main.service.py` 的 **Kiramei/baas-dev 服务版 dev 通道**。旧 GUI 稳定版不具备这里要求的协议，选择 `stable` 会被拒绝。首次安装必须明确确认，`--yes` 不绕过这一步。

CLI 配置目录默认是 `$XDG_CONFIG_HOME/baas` 或 `~/.config/baas`。使用 `--config-home <目录>` / `BAAS_CLI_HOME` 可以隔离不同安装：

```sh
baasx --config-home ./baasx-lab --demo
```

## 连接已有服务

### WebSocket 服务

在兼容的 `baas-dev` 后端目录启动服务：

```sh
python main.service.py --host 127.0.0.1 --port 8190
```

另开终端运行 BAASX：

```sh
baasx --server ws://127.0.0.1:8190 --lang zh
```

在提示中输入服务登录 Key。首次连接尚未初始化的服务时，输入的 Key 会初始化服务；已有服务应使用它原本的 Key。工作台内也可以 `/connect ws://127.0.0.1:8190` 切换地址。

另一台电脑上的服务应使用其实际可访问地址；示例里的 `127.0.0.1` 仅代表当前电脑。BAASX 复用签名公钥固定、身份认证和加密业务通道。自部署使用不同签名公钥时，通过 `--server-key <公钥>` 或 `BAAS_SERVER_SIGN_PUBLIC_KEY` 显式指定，不能通过跳过验证解决不匹配。

脚本使用 `BAAS_KEY` 环境变量提供 Key。它不写入 `settings.json`；避免把真实 Key 放进共享脚本或文档。连接的命令行参数、环境变量和保存偏好详见[CLI 参考](./cli)。

### 本地 socket / 命名管道

Unix 示例：

```sh
python main.service.py --host 127.0.0.1 --pipe-name /tmp/baasx.sock
baasx --pipe /tmp/baasx.sock profiles
baasx --pipe /tmp/baasx.sock
```

Windows 使用后端实际创建的命名管道路径。不要照抄另一个进程临时生成的路径；确保当前用户有访问权限。

## 更新、重载和退出

| 操作                | 作用                                                                   |
| ------------------- | ---------------------------------------------------------------------- |
| `/reload` 或 Ctrl+R | 重载工作台，重读偏好和指令包，恢复连接后返回总览；未保存编辑草稿会清除 |
| `/check-update`     | 检查 CLI 管理的本地后端 / OCR 更新                                     |
| `/update`           | 检查并应用本地环境更新                                                 |
| 替换 BAASX 发行包   | 升级终端程序本身；`/reload` 不会升级可执行文件                         |
| `/quit`             | 退出 BAASX                                                             |

应用本地更新前，CLI 所持有后端的所有配置档都必须没有正在运行的任务、调度和等待队列；其他 CLI 实例仍使用该环境时也会阻止替换。`--server` / `--pipe` 连接的外部服务不由这里更新。

退出 CLI 会关闭本次 CLI 自己启动的本地后端。外部服务及已提交任务则继续运行。需要常驻后台服务时，自行启动服务后用 `--server` 或 `--pipe` 连接；不要把关闭终端当作停止远程任务的方法。
